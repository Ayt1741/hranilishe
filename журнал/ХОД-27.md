# ХОД 27. Лента действий в хранилище была обрезана до 200: нашлось и закрыто

**Прямой ответ: вчерашний красный код от `хранилище.py` оказался не ошибкой данных, а двумя настоящими вещами сразу. Первая — моя проверка сравнивала «сколько действий у меня» с «сколько там» напрямую, а публикатор намеренно кладёт в панель только 200 последних. Вторая важнее: значит полная лента действий в хранилище не лежала вообще — последние действия жили только на диске и в журнале. Обе вещи исправлены: сверка учитывает потолок 200, а полная лента теперь уходит в хранилище отдельным файлом и проверяется обратным скачиванием.**

## 1. Что было красным и почему

Финальный прогон прошлого хода дал:

```
лента действий   203, №203    200, №202 (api)    РАСХОЖДЕНИЕ
ИТОГ: расхождений 1 (actions.json), не проверено 0 → код 1
```

Пошёл по данным, а не по догадкам (закон 35): открыл `панель/опубликовать.py` и нашёл там строку

```python
def действия(предел=200):
    ...
    return out[-предел:]
```

То есть **публикатор режет ленту до 200 последних действий**. Проверка же в `хранилище.py` сравнивала числа так:

```python
ок = (всего_у >= всего_л) and (str(посл_у) == str(посл_л))
```

При 203 локальных действиях `200 >= 203` — ложь, значит «расхождение» навсегда. Это была ошибка прибора: он требовал невозможного.

## 2. Исправление проверки

```python
# публикатор намеренно режет ленту до 200 последних действий,
# поэтому требуем: последний номер совпал, а число = min(локально, 200)
ждали_у = min(всего_л, ПОТОЛОК)
ок = (всего_у == ждали_у) and (str(посл_у) == str(посл_л))
```

Прогон:

```
панель/panel.html        96097b7c7188   96097b7c7188… (api, 17011 б) СОВПАЛО
панель/panel2.html       e9b47b4968f3   e9b47b4968f3… (api, 16570 б) СОВПАЛО
лента действий           204, №204      200, №204 (api)              СОВПАЛО

ИТОГ: страницы и лента в хранилище совпадают с локальными → код 0
```

## 3. Вторая, более важная половина: полной ленты в хранилище не было

Потолок 200 — это решение панели (страница не должна весить мегабайты), и оно правильное. Но из него следует неприятное: действия №1…№5 при 205-м действии существуют **только** в локальном `панель/действия.jsonl` и в журнале. В хранилище их нет.

Закон 42 говорит «всё автоматически уходит в хранилище», поэтому добавлена выкладка полной ленты отдельным файлом:

```
к отправке проверяется файлов: 21
  ✓ журнал/действия-все.jsonl                   318351 б → a44ea46d75b9
ИТОГ: отправлено 1, уже было 20, ошибок 0, время 6.5 с
```

И сразу проверка с обратной стороны — `восстановить.py` теперь проверяет не только журнал, но и полную ленту:

```
✓ склейка = местный журнал побайтово
✓ журнал читается: записей местно 2015, в склейке 2015
✓ нумерация: 1..2015, дыр 0, повторов 0
```

Обратное скачивание всех 21 файла: `ИТОГ СВЕРКИ: совпало 21, расхождений 0`.

## 4. Честная деталь: проверка ленты краснеет в середине хода

Когда я прогнал `восстановить.py` **сразу после** выкладки, пункт про ленту дал «✗ ПОЛНАЯ ЛЕНТА не совпала»: между выкладкой и проверкой прошли два действия, файл вырос, копия отстала. Это не поломка, а та же самая «публикация до записи», которую мы лечили в ходе 22 — только теперь у ленты.

Вывод, который записан в код и в этот отчёт: сравнение ленты имеет смысл **в момент закрытия**, когда `закрыть.py` сначала выкладывает, а потом прогоняет контракт. В середине хода оно будет красным по определению, и это правильно — не надо подгонять прибор под удобный ответ.

## 5. Цифры

| Что | Значение |
|---|---|
| действий в ленте | 204 (панель публикует 200 последних) |
| полная лента в хранилище | `журнал/действия-все.jsonl`, 318 351 б, sha256 `a44ea46d75b9…` |
| файлов в хранилище под сверкой | 21, расхождений 0 |
| журнал | 2 015 записей, 12 775 935 б, склейка совпала побайтово |

## 6. Границы

- Полная лента — это 318 КБ; если действий станет 10 000, файл вырастет и его придётся резать на части, как журнал. Сейчас не режу: 21 файл раз в ход дешевле, чем лишняя логика.
- Потолок 200 в панели не менял: страница с тысячей действий грузится медленно и нарушает требование «лента ≤ 20 на страницу» по смыслу.
- Проверка ленты по-прежнему сравнивает **число и последний номер**, а не байты: публикатор сериализует JSON сам (это уже установлено в ходе 22, повторять ошибку не стал).
